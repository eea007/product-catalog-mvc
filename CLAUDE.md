# product-catalog-mvc — conventions

This project is a Spring MVC mirror of product-catalog-reactive, fully 
implemented. It is a learning reference and is not deployed (no CI/CD).

CURRENT GOAL: complete, working implementations of every class, mirroring 
REACTIVE's behavior with the MVC idioms below. Validation for now is 
compile-only: mvn test-compile must succeed. The app does not need to be 
run, and no database or LocalStack is required yet.

Reference documents:
- docs/gap-report.md — inventory of REACTIVE vs MVC, gap table, and the 
  defects found in REACTIVE (§10). Read the relevant REACTIVE classes 
  before implementing each MVC counterpart and mirror their behavior.
- docs/class-map.md — generated by this work (see Deliverables).

## Project basics
- Maven, groupId com.example. Keep the existing base package of this project.
- Match REACTIVE's Spring Boot version (3.5.13) and Java version.
- Port 8080 (REACTIVE uses 8081).
- Lombok on entities: @Data, @NoArgsConstructor, @AllArgsConstructor, 
  @Builder, with lombok.* imports.
- Constructor injection via @RequiredArgsConstructor with private final 
  fields. No field injection.

## Dependencies (pom.xml)
- spring-boot-starter-web, -data-jpa, -validation, -actuator, 
  -security, -oauth2-resource-server
- postgresql (runtime), h2 (test)
- lombok
- Spring Cloud AWS (SNS, S3, Secrets Manager) — same BOM version as REACTIVE

- spring-boot-starter-test, spring-security-test (test)

## API contract
- Endpoints, paths, query params, JSON field names, and status codes must 
  match REACTIVE exactly, so the React UI could point at either service.
- The only intended contract difference: the price response record adds a 
  "converted" boolean field.

## Layering
- Controller (@RestController) → Service → Repository / Client / Publisher.
- Controllers bind input, call one service method, and return the result. 
  No try/catch, no repository, no RestClient, no AWS SDK in controllers.
- Services own validation (throwing IllegalArgumentException with the same 
  rules and messages as REACTIVE), entity/record mapping, and 
  @Transactional boundaries.
- Remote calls (HTTP or AWS) must never happen inside a transaction. When 
  a service method needs both, do the remote call outside the transactional 
  method (e.g., a separate bean or a non-transactional method that calls a 
  transactional one on another bean — never self-invocation).
- Spring AI tools call services or client classes, never repositories.
- Clients, publishers, and repositories never call services.

## Error handling
- GlobalExceptionHandler (@RestControllerAdvice) returning ProblemDetail:
  - IllegalArgumentException → 400
  - ProductNotFoundException (custom, in service/ or model/) → 404
  - MethodArgumentNotValidException → 400
  - downstream failures surfaced to callers → 503
- Status codes and error bodies must match what REACTIVE returns for the 
  same situations; where REACTIVE returns a plain status with no body, 
  a ProblemDetail body is acceptable.

## Package layout
- controller/  — @RestController classes
- service/     — business logic, @Transactional
- repository/  — JpaRepository interfaces
- domain/      — JPA entities
- model/       — request/response records, events, composite shapes
- client/      — RestClient wrappers (CurrencyClient, InventoryClient)
- messaging/   — SNS publisher and @TransactionalEventListener
- storage/     — S3 image storage adapter
- assistant/   — Spring AI tools and assistant service
- config/      — security, CORS, RestClient beans, AWS SDK clients, AI model

## Translation table (REACTIVE → MVC)
- RouterFunction + Handler → @RestController
- Mono<T>/Flux<T> → T / List<T> / Optional<T>
- switchIfEmpty(notFound) → orElseThrow(ProductNotFoundException::new)
- onErrorResume in handlers → GlobalExceptionHandler
- R2DBC ReactiveCrudRepository → JpaRepository (same derived query names)
- SchemaInitializer → not needed (spring.jpa.hibernate.ddl-auto=validate 
  in the default profile; create-drop in tests)
- WebClient → RestClient in a client class
- Async AWS SDK clients → sync clients (SnsClient, S3Client)
- Event published in reactive chain after save → service publishes a Spring 
  application event (record in model/) via ApplicationEventPublisher; a 
  @TransactionalEventListener(phase = AFTER_COMMIT) in messaging/ calls the 
  SNS publisher. Comment this as a deliberate difference.
- SNS message body and attributes must match REACTIVE exactly 
  (STOCK_DEPLETED payload shape), so inventory-service could consume either.
- Multipart upload via ServerRequest → MultipartFile parameter; same S3 key 
  format and response as REACTIVE.
- CorrelationIdWebFilter → CorrelationIdFilter from services-shared-lib, 
  registered in the filter chain.
- Handler tests bound to the router → @WebMvcTest with the security 
  filter chain active.

## Data
- Entities match REACTIVE's table and column names 
  (GENERATED ALWAYS AS IDENTITY → @GeneratedValue(strategy = IDENTITY)).
- Request/response shapes are records in model/. Never bind request 
  bodies directly to entities. Mapping lives in the service (or a small 
  mapper class in service/).
- The create request record has no id field, so callers cannot supply or 
  overwrite an id.
- Bean Validation annotations on request records where REACTIVE's rules 
  allow it, with @Valid on controller parameters; keep the service-level 
  IllegalArgumentException checks too.
- spring.jpa.open-in-view=false.

## Concurrency
- Plain synchronous code (REACTIVE has no Mono.zip or parallel work).
- spring.threads.virtual.enabled=true.

## Do not port (defects found in REACTIVE — see docs/gap-report.md §10)
Implement the corrected behavior and note the fix in a short comment:
- Dead 8 s response timeout: RestClient uses connect 5 s / read 3 s only 
  (via the request factory).
- Currency fallback mislabeling: on currency-service failure or timeout, 
  return the USD amount labeled "USD" with converted=false, and log a 
  warning. Successful conversions return converted=true.
- Untimed inventory-service calls from the assistant: InventoryClient with 
  5 s / 3 s timeouts and a fallback the tool can report to the model 
  (e.g., "inventory data unavailable") instead of throwing.
- Unused SQS client/queue URL and the prometheus actuator exposure: omit.
- The OPTIONS-200 filter: omit; use a CorsConfigurationSource in 
  SecurityConfig allowing localhost dev origins (property-driven list).

## Security
- OAuth2 resource server validating Cognito JWTs; issuer URI as a property 
  with REACTIVE's value.
- Public vs protected paths match REACTIVE exactly.
- Stateless sessions, CSRF disabled (token-based API).

## Profiles
- default/local: PostgreSQL connection properties (localhost), SNS topic 
  ARN / S3 bucket / service URLs as properties, anthropic-api-key from an 
  environment variable (${ANTHROPIC_API_KEY:}).
- aws: spring.config.import of the same Secrets Manager secrets REACTIVE 
  uses, CloudWatch metrics export enabled 
  (management.cloudwatch.metrics.export namespace).
- CloudWatch export disabled by default outside the aws profile.

## Assistant
- Endpoint /assistant/chat, matching REACTIVE's request/response contract.
- Same tools, tool names, and descriptions as REACTIVE, implemented as 
  Spring AI @Tool methods calling ProductService and InventoryClient.
- Same system prompt as REACTIVE.
- API key from the anthropic-api-key property.
- Model name from a property, defaulting to claude-sonnet-5.
- Custom AnthropicChatModel bean that does not send temperature, top_p, 
  or top_k (bypass autoconfiguration the same way REACTIVE does).
